# Anvil — Bug Ledger

This file is a primary artifact of the project, not documentation about it. It is the evidence behind every correctness claim in the [README](README.md), and it is the thing an interviewer will ask to see.

**Three rules, non-negotiable:**

1. **Every row has a seed.** If `anvil-sim --seed <seed> --commit <sha-before-fix>` does not reproduce the failure, the row is not real. Delete it.
2. **Every row has a pinned regression test.** `test/corpus/<ANV-id>.seed` runs in CI forever. It must fail on the parent of the fix commit and pass on the fix commit; CI verifies both directions.
3. **The ledger is written the day the bug is found.** A ledger reconstructed from memory in the final week is a liability — it will have wrong seeds, vague root causes, and an interviewer will find that out in one question.

---

## Row schema

```yaml
id:              ANV-0001                 # monotonic, never reused
title:           one line, states the defect, not the symptom
status:          open | fixed | wontfix | invalid | duplicate-of:ANV-XXXX
severity:        S0 | S1 | S2 | S3 | S4
class:           safety | durability | liveness | resource | performance | test-infra | spec-divergence
layer:           lsm | mvcc | raft | shard | txn | client | sim | checker | spec
invariant:       INV-RAFT-04              # the predicate that caught it, or "none — found by X"
found_by:        dst-random | dst-coverage-guided | dst-dpor | tlc | trace-validation | jepsen | unit | real-cluster | code-review
api_visible:     yes | no | conditional   # ← the column that justifies protocol-aware DST
seed:            0x8f3a91c40d2e77b1
config:          workloads/tpcc_5node.toml @ sha256:...
commit_found:    <sha>
sim_time_to_detect: 02:14:07              # simulated time from run start to violation
runs_to_first_hit:  1 in ~4,200 seeds     # how rare; drives whether a BUGGIFY site is needed
faults_minimised:   [partition{n1,n2|n3,n4,n5}, clock_skew(n4,+840ms), BUGGIFY@raft/log.cc:412]
root_cause:      one paragraph, mechanism not narrative
fix_commit:      <sha>
regression:      test/corpus/ANV-0001.seed
invariant_added: INV-RAFT-16              # if the bug motivated a new predicate
lesson:          what changed in how we build or test, if anything
```

**`api_visible` decision rule.** Mark `no` only if you can argue that no sequence of client operations could have observed the divergence — because the corrupted state was subsequently overwritten, garbage collected, masked by a snapshot, or existed only on a replica that never served a read. Mark `conditional` if a specific later access pattern would have exposed it. Be strict here; overstating this column is the fastest way to lose credibility, and the honest number is impressive on its own.

## Severity

| Level | Meaning | Response |
|---|---|---|
| **S0** | Client-visible correctness violation: lost acked write, stale read under a linearizable mode, isolation anomaly below the declared level, phantom data | Stop the phase. Fix before anything else. Post-mortem in the row. |
| **S1** | Internal invariant violated with no client-visible effect *yet* — corrupt Raft log, GC below a live snapshot, range coverage gap | Fix in the current phase. These are the protocol-aware DST wins; write the `api_visible: no` justification carefully. |
| **S2** | Liveness: permanent stall, livelock, non-converging state, unresolved intent after quiesce | Fix in the current phase. |
| **S3** | Resource or performance: leak, unbounded growth, write stall, pathological amplification | Backlog with a deadline. |
| **S4** | Test infrastructure: simulator, checker, harness, or spec defect | Fix immediately — an unreliable harness invalidates every result after it. |

## Workflow

```
 nightly fleet fails
        │
        ▼
 auto-dedup by (invariant, minimised fault signature, top-3 stack frames)
        │
        ▼
 minimiser runs: delta-debug the fault schedule to a minimal reproducing set
        │
        ▼
 candidate row auto-filed to BUGS.md as `status: open, triage: pending`
        │
        ▼
 weekly triage: confirm, classify severity + api_visible, assign
        │
        ▼
 fix + pin seed to test/corpus/ + CI asserts fail-before / pass-after
        │
        ▼
 ask: "what invariant would have caught this sooner?" → add it to docs/INVARIANTS.md
```

The last step is the compounding one. Each bug should either be caught by an existing invariant (good — record the detection time) or motivate a new one (better — record the new invariant id in the row). A bug that produces neither means the harness got lucky.

```yaml
id:              ANV-0001
title:           Scheduler::run() extracts an event, then discards it if the deadline passed
status:          fixed
severity:        S4
class:           test-infra
layer:           sim
invariant:       none -- surfaced as a false INV-LIVE-07 (replica convergence) failure
found_by:        dst-random
api_visible:     n/a (harness defect)
seed:            10          # also 48; ~1 seed in 30 of the counter sweep
config:          workloads/counter, 7 nodes, faults drawn from seed
commit_found:    <initial commit> (see caveat above)
sim_time_to_detect: 00:00:20 (the deadline boundary itself)
runs_to_first_hit:  1 in ~30 seeds, but only observable if run() is called twice
faults_minimised:   [any profile that reaches max_time with work outstanding]
root_cause: |
  The run loop extracted the earliest event from the queue and only then compared
  its timestamp against the deadline, breaking out without putting it back. The
  event -- and any coroutine handle it captured -- was destroyed. Any caller that
  ran to a deadline and then continued (heal_and_settle, or two run() calls) lost
  exactly one wakeup. The affected coroutine was left parked forever with no
  pending work and no error.
  Presented as "one node never finishes recovery, and the simulation is idle".
  Four separate wrong hypotheses were chased first -- a bounded retry loop, a
  premature `done` check, unhealed disk faults -- because every one of them
  produced the same symptom. Only per-node state dumps (applied set vs durable
  file size vs pending events) narrowed it: the node's WAL was complete on disk,
  its recovery had stopped mid-scan, and the queue was empty.
fix:             peek at queue_.begin() and break *before* extracting
fix_commit:      <initial commit> (see caveat above)
regression:      test/corpus/ANV-0001.seed
invariant_added: none yet -- see lesson
lesson: |
  The harness needs its own invariants. "A task is parked but no event exists that
  could ever wake it" is a checkable predicate over scheduler state, and it would
  have named this bug instantly instead of costing an afternoon of protocol
  spelunking. Filed as future work: INV-SIM-09, orphaned-task detection at
  quiesce.
  Also: this is exactly the class of bug the project exists to argue about. It was
  invisible to every P0 test, needed a deadline plus a continuation plus a task
  parked at the wrong moment, and reproduced perfectly from a 64-bit integer.
```
</details>

```yaml
id:              ANV-0002
title:           heal_and_settle restored links but left per-message and per-operation faults armed
status:          fixed
severity:        S4
class:           test-infra
layer:           sim
invariant:       none -- caused false INV-LIVE-* failures
found_by:        dst-random
api_visible:     n/a (harness defect)
seed:            9, 10, 45 (of the 60-seed counter sweep)
config:          workloads/counter, faults drawn from seed
commit_found:    <initial commit> (see caveat above)
root_cause: |
  Partitions live in the network model's link table; message loss, duplication,
  reset, EIO and bit rot live in the models' own fault profiles. heal_and_settle
  cleared the first and not the second, so after "healing" the cluster kept
  dropping messages and failing reads indefinitely. Eventual synchrony was never
  actually established, which makes every liveness assertion unfalsifiable --
  they were failing for a reason that had nothing to do with the protocol.
fix:             NetworkModel::stop_injecting() and DiskModel::stop_injecting(),
                 called alongside heal_all()
fix_commit:      <initial commit> (see caveat above)
regression:      covered by test/sim_faults.cc liveness assertions
lesson: |
  Liveness assertions are only meaningful under eventual synchrony, so "the
  adversary has stopped" has to mean *all* of it has stopped. A partial heal is
  worse than no heal: it produces failures that look like protocol bugs and are
  not, which is how a liveness check earns a reputation for flakiness and gets
  commented out.
```

<summary><b>ANV-0003</b> · S2 · workload · <b>recovery treated a read error as end-of-log, then gave up forever</b></summary>

```yaml
id:              ANV-0003
title:           WAL recovery conflated EIO with a corrupt record, and abandoned the node on failure
status:          fixed
severity:        S2
class:           liveness
layer:           client (workloads/counter.cc)
invariant:       INV-LIVE-07 (replicas converge after faults heal)
found_by:        dst-random
api_visible:     yes -- the node stays permanently behind and serves stale reads
seed:            9 (5 nodes, EIO rate ~2%)
config:          workloads/counter, faults drawn from seed
commit_found:    <initial commit> (see caveat above)
root_cause: |
  Two distinct bugs in one function.
  First, the recovery scan broke out of its loop on *any* pread failure, treating
  a transient EIO exactly like a checksum mismatch. That silently truncates the
  log at an arbitrary offset and converts a recoverable device error into
  permanent data loss.
  Second, a failed boot simply returned. There was no crash to trigger another
  restart, so the node stayed dark for the rest of the run -- present in the
  cluster, alive as far as the process model was concerned, and holding none of
  its own data.
fix:             distinguish read errors from invalid records; retry recovery
                 without bound, since any retry cap is a decision to give up
fix_commit:      <initial commit> (see caveat above)
regression:      test/corpus/ANV-0003.seed
lesson: |
  "Stop at the first invalid record" is correct for a torn write and catastrophic
  for an EIO, and the two arrive through the same return value. This is a real
  storage-engine bug class, not an artifact of the toy workload, and it goes on
  the P2 hunting list: the LSM's WAL reader must never let an I/O error masquerade
  as end-of-log.
```
</details>

```yaml
id:              ANV-0004
title:           ENOSPC could never fire, and three crash-resolution faults were reported as dead
status:          fixed
severity:        S4
class:           test-infra
layer:           sim
invariant:       INV-SIM-08 (every enabled fault kind is exercised)
found_by:        dst-random (the coverage check itself)
api_visible:     n/a

root_cause: |
  Capacity was drawn uniformly over 64 KiB .. 4 MiB. A uniform draw over that

  than a couple of kilobytes, so ENOSPC was enabled in one run in eight and
  reachable in none of them.

  defect -- those outcomes only exist at crash time.

  crash-resolution kinds now require crashes to be possible before counting as
  enabled, and the four workload-dependent kinds are reported rather than
  asserted in sim_faults, with the assertion living in disk_crash where the
  conditions are constructed deliberately.
fix_commit:      <initial commit> (see caveat above)
regression:      the INV-SIM-08 assertion in test/sim_faults.cc
lesson: |
  The coverage check earned its place on its first run. Both of these were knobs
  that looked armed in the config, appeared in every profile dump, and could not
  fire -- the exact failure mode the check exists to catch, and one that is
  otherwise completely silent.
```

<summary><b>ANV-0005</b> · S4 · checker · <b>an armed invariant that could never fire</b></summary>

```yaml
id:              ANV-0005
title:           INV-CTR-02 is shadowed by INV-CTR-01 and cannot fire through the workload
status:          fixed
severity:        S4
class:           test-infra
layer:           checker
invariant:       INV-SIM-05 (an invariant that has never fired is presumed vacuous)
found_by:        dst-random (the non-vacuity assertion itself, on its first run)
api_visible:     n/a
commit_found:    P1 stream D
root_cause: |
  INV-CTR-01 (tick class, O(nodes)) asserts |applied| >= |promised| as a cheap
  proxy. INV-CTR-02 (epoch class) asserts the real property, promised subset of
  applied. For the counter workload the proxy strictly subsumes the real check:
  recovery always yields a *prefix* of the log, so a node missing a promised
  increment is always also short by count. The tick check fires first and stops
  the run, and the epoch check never gets a turn.
  It did not look that way at first. At 60 and 100 seeds INV-CTR-02 never
  appeared; at 300 seeds it did, which briefly looked like the shadowing being
  only partial. It is not. The scheduler evaluates tick class after every event
  and *additionally* evaluates epoch class on epoch boundaries, collecting both
  into one violation list -- so when a violation happens to be live on an epoch
  boundary, INV-CTR-02 reports the same defect INV-CTR-01 had already caught.
  That is co-firing, not detection, and counting it as coverage would have been
  exactly the false comfort INV-SIM-05 exists to prevent.
fix: |
  INV-CTR-02 stays armed -- it is the actual property and the size check is only
  an approximation of it, so deleting it would trade a real assertion for a
  proxy. It now has a targeted non-vacuity case instead: a node holding the
  right *number* of increments and the wrong ones, which INV-CTR-01 cannot see
  by construction.
fix_commit:      P1 stream D
regression:      test_inv_ctr_02_is_not_vacuous in test/sim_faults.cc
lesson: |
  A cheap tick-class proxy in front of an expensive epoch-class check will
  shadow it, and the shadowing is invisible from evaluation counts -- INV-CTR-02
  was being *run* constantly. Even firing counts are not enough on their own,
  because co-firing on an epoch boundary looks identical to detection. What
  distinguishes them is whether the invariant can catch something the proxy
  cannot, and the only way to know is to construct that case deliberately.
  Every future pair of (cheap proxy, real property) needs the same treatment.
  The wider point: the fleet's "invariant health" report must not count
  violations alone. An invariant needs a case it *uniquely* catches, or it is
  decoration.
```
</details>

## Spec-divergence log

Divergences found by TLA+ trace validation — cases where a real simulator execution does not refine the spec. Each is either an implementation bug (fix the code), a spec bug (fix the spec), or an abstraction gap (document the refinement mapping). All three outcomes are worth writing down; the third is the one that teaches the most.
